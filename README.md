## 三、项目简介

“髹饰录”以漆器髹饰工艺为核心内容，将传统文化资料转化为更适合数字媒介阅读和探索的交互形式。网站通过统一的视觉语言串联多个功能模块，使用户既能进行轻量的互动体验，也能逐步进入知识学习、器物考据和社区分享。

### 核心功能

1. **髹饰工坊**
   - 从材质、颜色和纹样中选择属性，尝试合成漆器配方。
   - 合成成功后解锁对应器物，查看器物图像、年代、描述和髹饰信息。
   - 通过组合、反馈和解锁机制降低传统工艺知识的理解门槛。

2. **知识图谱**
   - 按颜色、材质、纹样和技艺组织漆器知识。
   - 通过分类索引和详情页面展示传统称谓、来源、文化含义及关联内容。
   - 将分散的知识拆解为可浏览、可检索、可继续探索的节点。

3. **器物档案与个人探索**
   - 按年代浏览已经解锁的器物档案。
   - 记录已解锁器物、完成配方和探索进度。
   - 设置彩蛋与隐藏成就，鼓励用户继续发现相关文化内容。

4. **漆器文化交流广场**
   - 支持发布交流讨论、配方分享和彩蛋分享。
   - 支持内容分类、排序、点赞、评论及个人内容筛选。
   - 为用户提供从“了解”到“分享”的参与路径。

5. **用户中心与个性化设置**
   - 支持注册、登录和退出登录。
   - 支持查看个人档案、管理账号及调整音频相关设置。

## 四、设计理念

### 1. 让传统文化从“被观看”变成“可参与”

传统工艺信息往往以静态图文呈现，用户容易停留在浅层浏览。“髹饰录”将材料、色彩、纹样和工艺转化为可操作的选择，让用户先通过体验建立直观感受，再通过知识图谱和器物档案补充背景信息。

### 2. 以漆器的视觉特征建立统一界面语言

界面采用漆器相关的深色、朱色、金色和纸张肌理，结合印章、档案、工坊等视觉元素，营造传统工艺与数字展陈相结合的体验。各页面共享导航、字体、卡片、弹窗和反馈机制，保证网站作为一个整体运行。

### 3. 形成完整的文化体验闭环

用户可以在工坊中尝试组合，在档案中查看结果，在知识图谱中理解概念，在广场中分享发现，最后通过个人档案持续记录探索进度。各模块相互补充，而不是彼此独立的页面集合。

## 五、技术实现

- **页面技术**：HTML5、CSS3、原生 JavaScript
- **模块组织**：使用 JavaScript ES Modules 按页面和功能拆分代码
- **数据与交互**：本地静态数据、`localStorage` 探索记录及 Supabase 数据服务
- **账号与社区**：Supabase Auth、Supabase 数据表及 Row Level Security
- **视觉实现**：自定义 CSS，无 Bootstrap、Vue、React 等预设样式库
- **响应式设计**：针对桌面端及较窄屏幕进行布局适配

项目不依赖前端 UI 组件库。交互、布局、弹窗、卡片、筛选、状态反馈等功能均由项目代码实现。

## 六、核心功能实现与开发难点

### 1. 漆器合成与解锁系统

**技术实现**

- 使用 JavaScript 管理用户选择的材质、颜色和纹样属性。
- 将预设配方组织为结构化数据，通过属性组合匹配对应配方。
- 根据匹配结果执行不同的交互逻辑，包括合成成功、失败反馈和器物信息展示。
- 合成成功后，将对应器物的解锁信息写入 `localStorage`，用于记录用户的探索进度。
- 个人档案页面读取本地记录，展示已解锁器物及相关进度。

**开发难点**

1. **配方匹配：** 需要保证不同属性组合能够准确对应配方，避免属性选择顺序影响匹配结果。
2. **状态同步：** 属性选择、合成结果、器物解锁和个人档案之间需要保持一致，避免出现合成成功但档案未更新的情况。
3. **数据持久化：** 使用 `localStorage` 保存浏览器本地的解锁记录，解决页面刷新后状态丢失的问题。目前该记录不具备跨设备自动同步能力。

### 2. 交流广场：动态、评论与点赞

**技术实现**

项目使用 Supabase JS SDK 与 PostgreSQL 数据库交互，主要涉及以下数据表：

- `community_posts`：保存用户发布的动态及点赞统计等信息。
- `community_comments`：保存评论内容及其关联动态、发布用户等信息。
- `community_post_likes`：保存用户与动态之间的点赞关系。

前端通过 Supabase SDK 执行数据查询、插入和删除操作，并根据查询结果更新页面。

**评论功能**

1. 用户提交评论时，先检查输入内容是否为空，并获取当前登录用户身份。
2. 通过 `INSERT` 将评论写入 `community_comments`，关联对应的动态 ID 和用户 ID。
3. 写入成功后重新查询评论列表，更新动态详情中的评论内容和数量。
4. 使用提交状态标记和按钮禁用机制，防止用户连续点击造成重复提交。
5. 请求失败时保留输入内容并提示错误，避免用户需要重新输入。

**点赞功能**

点赞功能采用独立记录表，而不是单纯修改前端显示的数字。

1. 用户点击点赞按钮后，根据当前用户 ID 和动态 ID，向 `community_post_likes` 插入记录。
2. 取消点赞时，删除对应的用户点赞记录。
3. 通过数据库唯一约束 `UNIQUE (post_id, user_id)`，保证同一用户对同一动态最多只有一条点赞记录。
4. 使用 PostgreSQL 触发器监听点赞记录的 `INSERT` 和 `DELETE` 操作，自动更新 `community_posts.likes_count`。
5. 页面加载时查询当前用户的点赞记录，恢复对应动态的已点赞状态。

**开发难点与问题排查**

- **点赞记录与统计数字不一致：** 最初仅依赖前端状态难以保证统计准确。后续利用独立点赞表和数据库触发器，通过数据库触发器在点赞记录插入或删除时同步更新动态的点赞总数，使记录变更与统计更新在同一数据库事务中执行。
- **重复点赞：** 通过数据库唯一约束和前端请求中的重复操作拦截共同处理。
- **评论重复提交：** 通过 `commentSubmitting` 状态标记和按钮禁用控制提交过程。
- **数据权限：** 对相关数据表启用 Row Level Security（RLS），配置 `SELECT`、`INSERT`、`DELETE` 等策略，并使用 `auth.uid()` 限制用户只能操作符合其身份权限的数据。
- **数据异常：** 对数据库请求增加错误处理，避免查询失败时将演示数据误显示为真实社区内容。

### 3. 用户认证与个人档案

**技术实现**

使用 Supabase Auth 提供注册、登录和退出登录功能，通过 Supabase 客户端管理用户会话。

主要处理流程：

1. 用户提交注册或登录信息。
2. 前端调用 Supabase Auth 对应的认证方法。
3. 认证成功后获取用户会话和身份信息。
4. 页面根据当前认证状态调整登录入口、用户信息及社区操作权限。
5. 用户退出登录时清除当前认证会话，并更新页面状态。

社区动态、评论和点赞记录均与用户 ID 关联，通过认证信息确定数据的归属。

**开发难点**

- **跨页面认证状态：** 不同 HTML 页面需要共享同一 Supabase 项目和客户端配置，避免页面之间的用户状态不一致。
- **访问权限控制：** 前端需要根据登录状态控制交互入口，数据库端则通过 RLS 再次验证用户身份，不能只依赖前端限制。
- **线上认证回调：** 本地开发地址与正式域名不同，需要在 Supabase Authentication 的 URL Configuration 中配置 Site URL 和 Redirect URLs，否则线上注册、登录后的跳转可能出现异常。
- **本地与云端数据区分：** 当前器物解锁记录主要由 `localStorage` 管理，社区数据由 Supabase 管理，两者采用不同的持久化方式。

### 4. 异步请求与加载状态管理

**技术实现**

社区数据查询、评论提交、点赞操作和用户认证等功能都涉及异步请求。项目使用 JavaScript 的 `async/await` 管理请求流程，并通过请求状态控制界面反馈。

主要处理方式：

- 请求开始时设置加载状态。
- 请求执行期间禁用对应操作按钮，避免重复提交。
- 请求成功后更新页面数据。
- 请求失败时捕获异常并显示错误提示。
- 在 `finally` 中恢复按钮和加载状态，避免请求异常后界面一直处于加载状态。

对于耗时较短的请求，采用延迟显示加载动画的方式，减少动画闪烁。不同操作使用对应的局部加载反馈，避免整个页面被不必要的遮罩覆盖。

### 5. 多页面架构与部署

**技术实现**

项目采用原生多页面架构，各页面分别使用 HTML 构建结构，通过 CSS 统一视觉规范，并使用 JavaScript ES Modules 拆分页面逻辑和公共功能。

- HTML：负责页面结构和内容组织。
- CSS：负责布局、响应式适配、组件样式和交互状态。
- JavaScript：负责页面事件、数据处理、功能逻辑及 Supabase 请求。
- Supabase：提供认证、社区数据存储和数据库访问控制。
- localStorage：保存浏览器本地的用户探索记录。

**部署流程**

1. 使用 Git 和 GitHub 管理项目代码，通过 `main` 分支维护正式版本。
2. 将 GitHub 仓库连接至 Cloudflare Pages。
3. 配置静态网站构建命令，将 HTML、CSS、JavaScript、字体、图片和音频等资源复制到 `dist` 目录。
4. 配置 Cloudflare Pages 自定义域名，使用独立域名访问网站。
5. 在 Supabase 中配置正式域名的认证回调地址。
6. 每次向 `main` 分支推送代码后，由 Cloudflare Pages 自动构建和部署。

**开发难点**

- **静态资源路径：** 部署时需要保证 HTML 引用的 CSS、JavaScript、图片、字体和音频文件均被复制到正确目录。
- **本地与线上环境差异：** 需要分别检查本地文件路径、线上资源加载、Supabase 连接和认证跳转。
- **部署版本验证：** 通过 Cloudflare Pages 的部署记录核对 Git 提交版本，区分代码未更新、构建失败和浏览器缓存等问题。
- **数据库与前端联调：** 部分问题需要同时检查前端请求、Supabase 数据表、RLS 策略和数据库触发器，不能仅通过页面表现判断故障原因。

### 音频来源

背景音乐来自 [Pixabay](https://pixabay.com/)，按 Pixabay 内容许可使用，存放于 `audio/` 目录：

- `click.mp3`：按键音效
- `success.mp3`：合成成功反馈音
- `bgm.mp3`：循环背景音乐

具体的播放、音量与开关逻辑由 `js/audio.js` 控制，浏览器通常要求用户先与页面交互后才允许播放音频。

### 关于 `js/vendor/`

该目录存放 Supabase JS SDK v2 及其子模块（auth、postgrest、storage、realtime、functions 等）的本地化 ES Module 副本，作为 CDN 加载的备选方案保留。由于时间原因，**当前线上代码并未引用该目录**，`js/supabaseClient.js` 仍通过 jsdelivr CDN 加载 SDK。如需摆脱 CDN 依赖（如离线环境或锁定版本），可将 `supabaseClient.js` 中的 import 路径改为本地 `./vendor/supabase-js@2.esm.js`。

### 待完成

- **vendor的本地化**：当前线上代码并未引用该目录，`js/supabaseClient.js` 仍通过 jsdelivr CDN 加载 SDK。如需摆脱 CDN 依赖（如离线环境或锁定版本），可将 `supabaseClient.js` 中的 import 路径改为本地 `./vendor/supabase-js@2.esm.js`。

- **中英文切换**：目前尚未找到合适的实现方式，功能未完成。候选方向包括基于 `data-i18n` 属性的轻量字典方案、构建期生成双语静态页面，以及引入成熟的 i18n 库；需要同时解决的问题是知识图谱与器物档案中大量结构化文本的翻译组织方式。

- **移动端适配**：当前版本仅支持桌面端，未优化移动端显示。目前收到反馈表示登录功能异常。后续计划包括响应式布局、移动端导航菜单、移动端操作流程优化等。
